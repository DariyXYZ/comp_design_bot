# Стандарт C#-сервисов бюро

Для серверных приложений на .NET: боты, HTTP API, фоновые службы. Не для
плагинов Rhino/Grasshopper — у них свой документ (`INDTools/docs/team/`),
общие с ним разделы отмечены. Отклонение допустимо, но записывается в README
проекта.

## 1. Базовые настройки

- Актуальный **LTS .NET** (сейчас .NET 10), версия SDK закреплена в `global.json`.
- Одно решение `.sln`; проекты в `src/`, тесты в `tests/`.
- Общие настройки компиляции — в `Directory.Build.props`: `Nullable`,
  `ImplicitUsings`, `TreatWarningsAsErrors`, `LangVersion latest`.
- Версии пакетов — централизованно в `Directory.Packages.props`
  (как в INDTools). В `.csproj` только имя пакета.
- `.editorconfig` в корне; форматирование проверяется `dotnet format`.
- Git, `README.md`, `.gitignore` (bin/obj/publish/wwwroot-сборка).

## 2. Структура

```
service-name/
├── ServiceName.sln
├── global.json
├── Directory.Build.props
├── Directory.Packages.props
├── .editorconfig
├── src/ServiceName/
│   ├── Program.cs               # композиция: конфиг, DI, конвейер, маршруты
│   ├── Config/                  # options из переменных окружения, валидация
│   ├── Endpoints/               # HTTP-вход: группы minimal API, webhook
│   ├── Features/<domain>/       # предметная логика: сервисы, модели, тексты
│   ├── Infrastructure/<system>/ # клиенты внешних систем: HTTP, БД, очереди
│   ├── Assets/                  # файлы, нужные в рантайме (копируются в output)
│   └── wwwroot/                 # статика, если сервис её раздаёт
├── tests/ServiceName.Tests/
├── .github/workflows/
└── README.md
```

Папки создаются по мере необходимости. Пустые `Features/`, `Assets/`,
`wwwroot/` заранее не заводятся.

## 3. Ответственность слоёв

**`Endpoints/`** — принять запрос, проверить вход, вызвать один сервис,
отдать ответ. Никакой предметной логики: если в обработчике появилось
условие «а если статус такой-то» — это уже `Features/`.

**`Features/<domain>/`** — сценарии предметной области: что такое заявка, как
она рендерится, что происходит при смене статуса. Здесь тексты для людей,
правила, модели. Не знает про HTTP и не парсит JSON внешних систем.

**`Infrastructure/<system>/`** — один клиент на внешнюю систему (`PyrusClient`,
`TelegramNotifier`). Авторизация, сериализация, повторы, таймауты. Без
предметной логики; наружу отдаёт свои типы, а не сырой JSON.

**`Config/`** — типизированные options, привязанные к переменным окружения и
проверенные на старте (`ValidateOnStart`). Сервисы получают options, а не
`IConfiguration`.

## 4. Направление зависимостей

```
Endpoints → Features → Infrastructure → BCL
```

Разрешено: `Endpoints → Features`, `Endpoints → Infrastructure` (только
чтобы передать зависимость), `Features → Infrastructure`. Запрещено:
`Infrastructure → Features`, `Features → Endpoints`. `Config` доступен всем.

Признак нарушения: клиент внешней системы знает названия статусов заявки —
значит, эти знания должны жить в `Features/`, а клиент принимать их
параметром.

## 5. Конфигурация и секреты

- Источник конфигурации — **переменные окружения**. `appsettings.json` только
  для логирования и того, что не отличается между стендами.
- Секреты не попадают в репозиторий, логи и ответы API. `.env`-файлы — только
  для локального запуска и в `.gitignore`.
- Все переменные перечислены в README таблицей: имя, обязательность,
  назначение. Отсутствие обязательной переменной валит старт с понятным
  сообщением, а не первый запрос.
- Поведение, зависящее от окружения (регистрация webhook, адрес публичного
  хоста), включается явной переменной, а не угадывается.

## 6. HTTP и внешние системы

- Minimal API; маршруты одной области — в одном файле `Endpoints/<Area>Endpoints.cs`
  с методом расширения `Map<Area>()`.
- Ответы — JSON в camelCase, ошибки — `{ "error": "..." }` со статусом
  4xx/5xx. Формат согласуется с клиентом и не меняется молча.
- Клиенты внешних систем — typed `HttpClient` через `IHttpClientFactory`,
  с явным таймаутом. Сбой внешней системы не должен ломать то, что уже
  сделано: сначала критичная запись, потом уведомления.
- Фоновая работа — `IHostedService`/`BackgroundService`, не `Task.Run` из
  обработчика.
- Windows-служба — `AddWindowsService()`; пути от `AppContext.BaseDirectory`,
  не от текущего каталога.

## 7. Код

- Именование — соглашения .NET: `PascalCase` типы и члены, `camelCase`
  локальные, `_camelCase` приватные поля, `I`-префикс интерфейсов. Файл —
  имя типа.
- Приватные поля — вверху класса; `sealed` по умолчанию; `record` для
  неизменяемых данных.
- Комментарий объясняет **почему**, а не что. XML-`<summary>` на публичных
  типах и методах, которые вызывают снаружи модуля. Магические константы —
  с комментарием об источнике значения (как в INDTools).
- Пользовательские тексты (сообщения бота, ответы человеку) — в одном месте
  модуля (`Texts.cs`), не разбросаны по обработчикам.
- Нет мёртвого и закомментированного кода. Изменил сигнатуру — проверил всех
  вызывающих.
- Исключения внешних систем ловятся на границе `Infrastructure`, наружу —
  `null`/результат с ошибкой и запись в лог; в `Features` не пишут `try/catch`
  вокруг каждого вызова.

## 8. Тесты

- `xunit`, проект `tests/<Service>.Tests`, запускается `dotnet test`.
- Юнит-тесты — на чистую логику `Features/` (рендер, разбор, правила).
- Тесты HTTP — через `WebApplicationFactory` с подменёнными клиентами
  внешних систем. В CI нет обращений к живым Pyrus/Telegram.
- Что проверяет тест, видно из имени: `Метод_Условие_Ожидание` или фраза.
- Регрессия на найденный баг добавляется вместе с фиксом.

## 9. Команды

```
dotnet restore
dotnet build --no-restore
dotnet test --no-build
dotnet format --verify-no-changes
dotnet publish src/<Service> -c Release -o publish
```

Одни и те же команды локально и в CI.

## 10. CI/CD

- GitHub Actions: `build → test → format` на PR и на `main`.
- Деплой — отдельный job после проверок, только с `main`, через
  self-hosted runner или артефакт. Секреты стенда — в GitHub Environments,
  не в workflow.
- Служба перезапускается после выкладки; workflow проверяет, что процесс
  поднялся (health-эндпоинт `/health`).

## 11. README

Обязательно: назначение, окружение, переменные окружения (таблица), запуск
локально, тесты, сборка и публикация, установка службы, архитектурные
решения, **отличия от этого стандарта**.

## 12. Чек-лист нового сервиса

1. `global.json`, `Directory.Build.props`, `Directory.Packages.props`, `.editorconfig`.
2. `src/<Service>` + `tests/<Service>.Tests`, оба в `.sln`.
3. Options из env с валидацией на старте; таблица переменных в README.
4. `/health`; логирование в файл или журнал стенда.
5. Workflow с `build/test/format`; деплой отдельно.
6. README с отклонениями.
