## 2. Один сервер, модули внутри него

Сохраняем `server/`: ASP.NET Core / .NET 10, один исполняемый проект плюс существующий тестовый проект. Это модульный монолит: функции отделены в исходниках, но запускаются и публикуются одним приложением.

Сохраняем `web/`: Next.js / React / TypeScript. В целевой production-сборке Next.js экспортирует статические файлы в `wwwroot` .NET-приложения [S1]. Страницы получают закрытые данные из API после входа, не из публичных JS/HTML-артефактов сборки.

Одна отдельная служба за существующим Caddy/согласованным HTTPS-шлюзом:

- `/` — интерфейс;
- `/api/…` — HTTP API;
- `/telegram/webhook` — входящие события Telegram.

**Уточнение 17.09.** Интерфейс открывается по прямой ссылке (Main Mini App в BotFather) из любого чата и должен работать как внутри Telegram, так и вне его. Заявка создаётся, статусы и комментарии смотрятся в интерфейсе через `/api/…`. Диалог заявки в боте, `sendData` и код входа в кнопке бота не поддерживаются: бот остаётся каналом для кнопок статусов в чате отдела и уведомлений (разрешение на сообщения — `requestWriteAccess` из Mini App). Контекст перехода по ссылке (тема, задача) передаётся через `start_param`.

Это отдельное приложение на компьютере AI01, не часть её процесса. Предложенный локальный адрес `127.0.0.1:5089`, DNS, внешний HTTPS и сертификат по-прежнему требуют подтверждения ИТ.

Фоновые обработчики работают в том же процессе; ASP.NET Core поддерживает hosted services [S2]. Отдельный broker/worker-server не вводим. Отсутствие отдельного брокера не снимает будущую задачу сохранения принятой работы.

## 3. Кто владеет какими данными

| Данные | Источник истины / место хранения |
|---|---|
| Карточка сотрудника, имя, корпоративная почта, отдел, признак действующего сотрудника | Pyrus: существующий кадровый реестр |
| Заявка, бизнес-статус, комментарии, основные вложения и проекты | Pyrus |
| Проверенная связь Telegram-аккаунта с карточкой сотрудника | Техническая БД приложения; не справочник кадровых данных |
| Сессии и одноразовые подтверждения, если для выбранного входа необходимо хранение | Техническая БД; только необходимые сведения и ссылки |
| Ход отправки заявки, входящие события, ожидающие доставки уведомления | Техническая БД |
| Прикладные роли администратора/исполнителя | Явная политика приложения по ссылкам на сотрудников; не копия HR-атрибутов. Начать с конфигурации, если не требуется административный UI |
| Короткоживущие данные сотрудника для отображения/проверки | Только ограниченный кэш; не второй постоянный реестр |
| Подписка сотрудника на задачу («следить») | Pyrus: штатные подписчики задачи (`subscribers_added` / `subscribers_removed` в комментарии). Требует учётной записи сотрудника в Pyrus, поэтому включается вместе с `EmployeeRef`. До этого — текущий механизм служебных комментариев; своя таблица не заводится |

Не создаём `Employees`/`EmployeeProfiles`, фоновую синхронизацию всех сотрудников или экран локального редактирования отдела, почты и трудового статуса. Не вводим фиктивную таблицу сотрудников только ради локального внешнего ключа.

Ссылка `PyrusEmployeeTaskId` в сессии или операции — не дублирование сотрудника. Данные HR остаются в Pyrus. Прикладная Telegram-привязка доказывает связь аккаунта с этой карточкой; сама по себе она не доказывает, что сотрудник всё ещё работает.

Правило: прежде чем добавлять таблицу в техническую БД, проверить, закрывает ли задачу штатная возможность Pyrus (подписчики, участники, поля формы). Дублирование того, что Pyrus уже хранит, не допускается.

Разрешены необходимые временные данные операции и минимальный аудит. Их срок хранения и состав будут определены отдельно; они не превращаются в редактируемый локальный справочник сотрудников или независимый реестр бизнес-статусов.

## 4. Идентификатор сотрудника

Предлагаемый идентификатор — **ID задачи-карточки сотрудника в кадровой форме Pyrus**. В API реестра у каждой задачи есть `id` [S3, S4]. Используем название `PyrusEmployeeTaskId` или тип `EmployeeRef`, который однозначно означает эту ссылку; новый локальный UUID сотрудника не нужен.

Не смешиваем:

- ID формы кадрового реестра;
- ID задачи-карточки сотрудника;
- внутренний порядковый номер сотрудника в поле формы;
- Pyrus member ID учётной записи;
- Telegram user ID;
- Pyrus task ID заявки в отдел.

Не предполагаем, что каждый сотрудник имеет полноценную учётную запись Pyrus. В предыдущем контексте фигурировала форма `2332518`, «0. Список сотрудников»; её актуальный состав и права доступа не проверены по рабочему API в этой сессии. Номера полей не зашивать по памяти и не менять кадровый реестр автоматически.

Уникальность карточки, архивные/уволенные сотрудники, повторное создание карточки и неоднозначное совпадение почты должны быть проверены при реализации directory. При неоднозначности не выбирать первую запись и не выдавать доступ молча.

Владение заявкой в целевой модели связано с `EmployeeRef`, а не с Telegram ID или изменяемой почтой. Способ записи ссылки в форму заявок и безопасное сопоставление старой истории — отдельная миграционная задача. В структурном рефакторинге старую авторизацию не переопределять под новый ID без проверки интеграции.

## 5. PyrusDirectory и вход — не одно и то же

`IEmployeeDirectory` — небольшой прикладной контракт получения сотрудника; `PyrusEmployeeDirectory` — его адаптер к кадровому реестру. Он возвращает нормализованное представление только для чтения, а не локальную EF-сущность.

Подтверждение личности выполняет отдельная логика входа. Наличие карточки в Pyrus не является паролем/SSO. Telegram — дополнительный канал привязки, не обязательное условие существования сотрудника.

**Уточнение 17.09.** Способов входа два, и модуль Identity проектируется под оба:

- внутри Telegram — проверка подписи `initData` и выдача токена сессии приложения (реализовано сейчас; секрет токена — отдельная переменная, не токен бота);
- вне Telegram — авторизация через Plancy (либо через Платформу, где она уже есть). Отложено, до конца года не реализуется; вход по почте и паролю не планируется, `Infrastructure/Mail` не создаётся.

Связка заявок, созданных через Telegram и через Plancy, решается на этапе Identity через `EmployeeRef`; отдельного решения сейчас не требуется.

Проверяем действительность сотрудника при входе и при обновлении сведений доступа по ограниченной политике свежести. Можно использовать короткий кэш в памяти; не нужен запрос в Pyrus для каждого изображения. Нельзя разрешать бесконечную работу по однажды скопированному признаку `active`.

При недоступности Pyrus и истёкших проверенных сведениях не выдавать новый доступ/повышение прав на основании локальной ссылки. Точный срок кэша, поведение существующих сессий и принятых операций согласуются в задаче входа, с явной верхней границей задержки отзыва. В начальной архитектуре автономная работа кадрового справочника не обещается.

## 6. Предлагаемая структура

Схема показывает целевые зоны ответственности.

```text
comp_design_bot/
├── web/
│   └── src/
│       ├── app/                  # страницы и layouts
│       ├── features/             # интерфейс заявок, каталога и т. п.
│       ├── components/           # общие UI-компоненты
│       ├── contracts/            # контракты HTTP API, не серверный код
│       └── lib/                  # клиент API и адаптер Telegram WebApp
├── server/
│   ├── src/CompDesignBot/
│   │   ├── Program.cs            # запуск и подключение составных частей
│   │   ├── Hosting/              # конфигурация, DI, middleware
│   │   ├── Features/
│   │   │   ├── Identity/         # вход, доступ, EmployeeRef, directory contract
│   │   │   ├── Requests/         # сценарии, правила, модели и API заявок
│   │   │   ├── Catalog/          # темы, материалы и проекты
│   │   │   ├── Feed/             # лента результатов
│   │   │   └── Notifications/    # намерение и состояние доставки
│   │   ├── Channels/
│   │   │   └── Telegram/        # webhook, кнопки статусов, уведомления (без диалога заявки)
│   │   ├── Infrastructure/
│   │   │   ├── Pyrus/           # HTTP-клиент, адаптеры и mapping полей
│   │   │   └── Persistence/     # EF Core / SQLite для технических данных
│   │   └── wwwroot/             # результат сборки web, не исходники данных
│   └── tests/CompDesignBot.Tests/
└── docs/architecture/
```

HTTP endpoint находится рядом со своей функцией, например `Features/Requests/RequestsEndpoints.cs`. Это не означает, что весь модуль должен зависеть от HTTP: транспорт остаётся тонким адаптером, а прикладной сервис не принимает `HttpContext`, `Telegram.Update`, сырые JSON-поля Pyrus или EF-сущность сотрудника.

`web/src/lib/server` и `web/src/app/api` удаляются: серверного кода в Next.js не остаётся, он дублировал бы `server/`. В `web/` остаются экраны, клиент HTTP API, адаптер Telegram WebApp и `contracts/` с типами ответов. Порядок удаления и переноса типов будет описан отдельно.

`Channels/Telegram` содержит поведение канала. Он вызывает те же прикладные сервисы, что HTTP endpoints, а не повторяет правила. Отправляющий Telegram-адаптер может находиться рядом с этим каналом; его выбирают при регистрации зависимостей.

`Infrastructure/Pyrus` не становится монолитным бизнес-сервисом: в нём детали протокола и mapping. Контракты, например `IEmployeeDirectory` и `IRequestRegistry`, принадлежат потребляющим функциональным модулям. Один общий механизм HTTP/auth, отдельные небольшие адаптеры для кадрового реестра и заявок.

Прикладные сервисы используют зависимости с ясными обязанностями. Для технического хранения применяем EF Core, не строим поверх него универсальный `GenericRepository<T>` или слой с единственной обязанностью передать вызов дальше. Не требуется интерфейс для каждого класса.

В рамках одного .csproj изоляция модулей — правило структуры, review и тестов, а не физическая граница отдельных assemblies. Циклические вызовы запрещены. Усложнять сборочную структуру ради формального количества слоёв не нужно.

## 7. SQLite как техническая БД

SQLite — встраиваемая транзакционная СУБД без отдельного серверного процесса [S5]. EF Core имеет поддерживаемый провайдер SQLite [S6]. Для одного экземпляра приложения с локальным техническим хранилищем это соответствует выбранной минимальной инфраструктуре. Высокую производительность при неизвестной нагрузке заранее не обещаем.

Ограничения выбранного режима: БД лежит на локальном диске сервера, вне `wwwroot`, Git и каталога заменяемого релиза; не на общей сетевой папке. Миграции, резервное копирование и восстановление должны быть частью отдельной задачи развёртывания. Активную БД нельзя бездумно копировать как обычный документ.

SQLite допускает одного одновременно пишущего writer; не держать транзакцию открытой во время сетевого вызова Pyrus/Telegram. При нескольких экземплярах сервиса или существенной конкуренции записей пересмотреть выбор в пользу серверной реляционной БД [S7]. Переход на другой provider потребует проверки миграций и переноса данных, а не только замены строки подключения [S8].

В первом архитектурном задании подключение SQLite и таблицы не реализуются: выбираем границу, затем реализуем нужную функциональность отдельными небольшими шагами.

## 8. Чего намеренно не добавляем

Не вводим микросервисы, отдельный Node backend, MongoDB, Redis, RabbitMQ, Kafka, Kubernetes, event sourcing, обязательный CQRS/MediatR или набор пустых Domain/Application/Infrastructure-проектов.

Не создаём универсальную интеграционную платформу, движок workflow или синхронизацию сотрудников «для будущего». Не меняем Next.js на другой UI-фреймворк. Не требуем физической доставки «ровно один раз», которой БД сама по себе не обеспечивает.

Простота не отменяет проверку прав, одинаковую бизнес-логику каналов, честные результаты операций и хранение принятой работы. Их реализация идёт после структурного шага, не одним огромным заданием.

## 9. Что уже видно в архиве

Статическое чтение исходников, не проверенная сборка:

- `server/src/CompDesignBot/Program.cs`: один host; API, бот, hosted services и static hosting уже объединены.
- `Features/Requests/RequestStore.cs`: работа с Pyrus и разный подход к ошибкам для бота/API; методы выборки ориентированы на Telegram ID.
- `Endpoints/RequestsEndpoints.cs`: транспорт одновременно выполняет orchestration Pyrus и Telegram.
- `Features/Requests/RequestRecord.cs`: `UserId` читается из поля Telegram ID; не переименовывать его в EmployeeId без реальной миграции.
- `Infrastructure/Pyrus/IPyrusClient.cs`, `PyrusClient.cs`: `SchemaAsync` и `RegisterAsync` привязаны к единственной `PyrusFormId`. Для второй кадровой формы нельзя использовать тот же глобальный schema-кэш без разделения по форме.
- `web/src/lib/server/`: типы и старые серверные реализации следует разделить до удаления Next.js backend.

Это основания для постепенного извлечения общей логики, а не для переписывания проекта с нуля.

## 10. Ближайшее действие

Согласовано 17.09. Порядок, каждый шаг — отдельная задача в ClickUp (список «0 - Архитектура»):

1. Перекладка `server/` по структуре §6 без изменения поведения; стандарт `docs/csharp-standard.md` приводится к этому документу (endpoints рядом с фичей).
2. Прикладной сервис заявок в `Features/Requests` (создать, сменить статус, комментарий, подписка), которого вызывают и HTTP, и `Channels/Telegram`; `POST /api/requests`; удаление диалога заявки и `sendData`; интерфейс отправляет форму через API.
3. `Infrastructure/Persistence`: SQLite, первые таблицы — входящие обновления Telegram и состояние ожидания текста в чате отдела (сейчас — память процесса).
4. Identity: `IEmployeeDirectory` / `PyrusEmployeeDirectory`, привязка Telegram-аккаунта к карточке, поле сотрудника в форме заявок, владение по `EmployeeRef`. Требует служебного аккаунта Pyrus с доступом к кадровой форме.
5. Notifications: очередь доставки с состоянием; подписки — штатные подписчики Pyrus.

Ветки: архитектурные изменения — в `development`; точечные задачи — ветками от `development`, в `main` — только через слияние для деплоя. До появления сервера на AI01 интерфейс для проверки из Telegram размещается на Vercel.
