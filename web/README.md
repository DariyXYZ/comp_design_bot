# comp_design_bot — Mini App

Mini App Отдела вычислительного проектирования IND — три раздела внутри
Telegram:

* **Темы** — свайп-колода из 8 карточек («когда звать нас») и под каждой темой
  то, что по ней уже готово: кейсы проектов, инструменты отдела и
  переиспользуемые модули с инструкцией «сделай сам».
* **Поток** — что отдел делает сейчас и что уже сделал, с путями к папкам.
* **Профиль** — кто вы для отдела; список заявок пока в чате бота (`/my`).

Заявка создаётся только из контекста — из темы или из конкретного решения — и
уходит боту через `sendData`; дальше бот просит картинки и показывает превью
перед отправкой в отдел.

Часть проекта [`comp_design_bot`](../README.md); бот на aiogram лежит в
[`../bot/`](../bot/).

## Требования к окружению

- Node.js 22+
- npm (в репозитории один lock-файл — `package-lock.json`)

## Установка

```bash
npm install
cp .env.example .env.local   # затем вписать реальные значения
```

## Запуск

```bash
npm run dev
```

Открывать по адресу с базовым путём: <http://localhost:3000/comp_design_bot>.

Вне Telegram выбор задачи недоступен (`sendData` есть только внутри клиента) —
кнопка покажет подсказку. Всё остальное — свайпы, флип, стрелки — работает в
обычном браузере.

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | Проект Supabase с таблицей `cases` |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Анонимный ключ, только чтение по RLS |

Обе публичные по дизайну: запрос уходит из браузера, значения попадают в бандл.
`anon`-ключу Row Level Security разрешает только `select` таблицы `cases`.
**Секреты сюда добавлять нельзя** — для них понадобится серверная часть, которой
у этой сборки нет (см. «Ограничение статического экспорта»).

Отсутствие переменной валит `next build` с понятной ошибкой
([`src/config/env.ts`](src/config/env.ts)) — молча собраться со сломанным
адресом нельзя.

В CI значения заданы переменными репозитория (Settings → Secrets and variables
→ Actions → Variables), не секретами.

## Архитектурные решения

### Ограничение статического экспорта

`output: 'export'` — сервера нет: экран читает Supabase прямо из браузера, а на
GitHub Pages серверного кода и быть не может. `basePath: '/comp_design_bot'`,
потому что это project-сайт, а не корень домена.

**Это упрётся в потолок на следующих фичах.** AI Q&A требует ключ Claude API
(нельзя в клиент), профиль «мои заявки» требует проверки подписи `initData`
(HMAC клиентским JS не проверить, RLS Supabase этого тоже не умеет). Оба
случая — серверный код, которого здесь нет. Варианты на тот момент: перенести
проект на Vercel (API routes рядом) либо оставить статику на Pages и добавить
Supabase Edge Functions. Решение отложено осознанно, а не забыто.

### Императивная колода

Внутренности деки в [`_components/case-deck.tsx`](src/app/_components/case-deck.tsx)
работают с DOM напрямую (`insertBefore`, `replaceChild`, `style.transform`), а не
через состояние React. Три причины, каждая из которых уже была источником бага:

1. Карточки живут внутри CSS-переходов, которые ререндер обрывает.
2. Второй слой стопки подменяется **посреди драга** — иначе после отпускания
   палец видит один кейс, а после анимации внезапно другой.
3. Гашение соседних карточек обязано быть инлайн-стилем: раскладка стопки сама
   держит там `opacity` инлайном, а инлайн не перебивается классом из стилевого
   листа.

React владеет статичной оболочкой (стрелки, CTA, подпись). Решения, которые
легко сломать незаметно — индексы обхода, порог свайпа, отличие тапа от драга,
строки трансформов — вынесены в чистый
[`_lib/deck-math.ts`](src/app/_lib/deck-math.ts) и покрыты юнит-тестами.

Будущие табы (каталог, лента, профиль) — списки и формы, там будет обычный
декларативный React. Императивность здесь ограничена одним компонентом
намеренно и не является образцом для остального кода.

### Размер карточки

Telegram открывает Mini App невысоким фреймом, и высота меняется при
разворачивании. Карточка обязана уменьшаться **целиком**, сохраняя пропорцию
5:7, а не сплющиваться по высоте.

Поэтому у `.deck` задана только ширина (`--card-w`), а высота выводится из
`aspect-ratio`. Ограничения по высоте там быть не должно: `max-height`
перебивает `aspect-ratio`, и карточка теряет форму — ровно это и происходило.

`--card-w` считается дважды:

1. В CSS — приблизительно, из `--tg-viewport-stable-height` (вне Telegram —
   `100dvh`) минус высота обвязки `--chrome-h`. Нужно, чтобы первый кадр до
   гидратации был близок к правильному.
2. В `sizeCard()` — точно, замером: свободную высоту даёт флексбокс
   (`.deck-wrap` растянут на остаток экрана), поэтому высоту обвязки считать
   руками не нужно. Пересчитывается на `resize`, на `viewportChanged` от
   Telegram и после загрузки шрифта.

CTA и позиции стрелок берут ту же переменную, поэтому кнопка всегда ровно по
ширине карточки.

Внутренние размеры карточки заданы в долях её ширины (`--cu`, аналог `cqi`, но
без `container-type` — контейнерное containment мешает 3D-флипу). Кегли
дополнительно ограничены снизу через `clamp`: чистая пропорция в самом низком
фрейме дала бы текст ~7px. Подсказка кейса обрезается по высоте с затуханием
последней строки — её длину правят в Supabase, поэтому подобрать размеры «чтобы
всегда влезало» нельзя.

### Жесты через Pointer Events

Единый поток `pointerdown/move/up/cancel`, не раздельные touch и mouse: на
тач-устройствах браузер синтезирует mouse-события **после** touch, и один тап
дважды переключал переворот карточки.

### Где живёт приложение

Приложение развёрнуто на **Vercel**: экраны и API-роуты рядом, поэтому CORS не
нужен, а секреты (токен бота, ключ Pyrus) остаются на сервере.

Статического экспорта больше нет — `output: 'export'` несовместим с
динамическими роутами, а без них не сделать личный кабинет: подпись данных
запуска проверяется только на сервере, и ключ Pyrus в браузер положить нельзя.
Поэтому GitHub Pages как площадка отключён (workflow остались с ручным
запуском, чтобы можно было откатиться), а черновики смотрим в preview-деплоях
Vercel.

Переменные окружения проекта:

| Переменная | Где нужна | Зачем |
|---|---|---|
| `SUPABASE_URL` / `SUPABASE_ANON_KEY` | сервер | карточки тем из таблицы `cases` (роут `/api/topics`) |
| `NEXT_PUBLIC_API_BASE` | клиент | пусто = API на этом же домене |
| `TELEGRAM_TOKEN` | сервер | проверка подписи запуска и подпись своих токенов |
| `PYRUS_LOGIN` / `PYRUS_SECURITY_KEY` / `PYRUS_FORM_ID` | сервер | чтение реестра формы заявок |

### Почему карточки читает сервер

Раньше браузер обращался в Supabase напрямую, и для этого ключ приходилось
пробрасывать через `NEXT_PUBLIC_*` — то есть вшивать в бандл. Теперь их читает
роут `/api/topics`, а ключ остаётся на сервере. Побочная выгода важнее
безопасности в этом случае: исчезла необходимость держать публичные копии
переменных, а `NEXT_PUBLIC_*` подставляются на этапе сборки, поэтому опечатка в
имени оставляла приложение без данных молча — ровно это и случилось при первом
деплое на Vercel.

### Личный кабинет

```
POST /api/auth/exchange   X-Telegram-Init-Data → { token, user }
GET  /api/requests        Authorization: Bearer … → заявки из Pyrus
```

Почему обмен на свой токен, а не проверка `initData` в каждом запросе: клиенты
Telegram отдают его непредсказуемо — после восстановления вебвью из кеша он
приходит пустым, и профиль застревал на «Гость». Подпись проверяется один раз,
дальше приложение живёт со своим токеном (HMAC-подпись, срок 30 дней, без
состояния на сервере).

Заявки отбираются по полю «Telegram ID» **на нашей стороне**: фильтры в
`forms/{id}/register` Pyrus молча игнорирует — проверено, фильтр по
несуществующему id возвращает весь реестр. Полагаться на него значит однажды
показать человеку чужие заявки.

### Канал до бота

У статического Mini App нет сервера, поэтому единственный путь к боту —
`sendData`: строка попадает в сообщение `web_app_data`, и Telegram закрывает
приложение. Из этого растут три следствия, видные в интерфейсе:

1. **Лимит 4096 байт**, причём байт UTF-8 — русский текст занимает по два на
   символ. Поля обрезаются до лимитов бота (`MAX_DESCRIPTION`, `MAX_SOURCE`)
   ещё в браузере, а переполнение payload показывается человеку, а не теряется
   молча (`features/requests/submit.ts`).
2. **Файлы не передаются.** Картинки просит бот в чате сразу после отправки —
   это шаг существующего FSM, а не обходной путь.
3. **Отправка возможна только внутри Telegram.** В браузере кнопка объясняет
   это текстом; чтобы поведение не сломалось незаметно, оно закрыто e2e-тестом
   (`tests/e2e/request.spec.ts`).

Контракт с ботом (`bot/handlers/create.py`, `from_webapp`): `case` — ключ темы,
обязателен; `description` включает «заполненный» путь (бот пропускает вопросы и
спрашивает только картинки); `project`, `origin`, `deadline` бот дописывает в
шапку описания, потому что карточка заявки в чате отдела рендерится из описания
и должна сохранить их при смене статуса. Ключи в payload — snake_case, их читает
Python.

### Данные

Карточки — единый источник с ботом: таблица `cases` в Supabase. Контент
правится в дашборде, не в коде. Кеширование выключено (`cache: "no-store"`):
правку в дашборде ждут увидеть при следующем открытии, данных мало (8 строк).
Бот подхватывает те же правки только после перезапуска, Mini App — сразу.

### Структура каталогов

Разделов стало три (темы, поток, профиль), поэтому папки из стандарта заведены
по факту появления кода:

```
src/
├── app/                     маршруты и сборка страниц
│   ├── _components/         колода и экран тем — код только этого маршрута
│   ├── _lib/                чистая логика колоды под тесты
│   ├── feed/  item/  my/  request/
├── components/
│   ├── layout/              оболочка, нижняя навигация, шапка экрана, полоса действия
│   └── ui/                  поле пути с копированием
├── features/                предметные модули, каждый со своим index.ts
│   ├── materials/           материалы под темами + строка списка
│   ├── feed/                поток задач отдела
│   └── requests/            заявки и шкала вех
├── config/                  env и карта маршрутов (navigation.ts)
├── hooks/                   общие клиентские хуки
├── lib/                     техническая инфраструктура
│   └── client/              обёртка над SDK Telegram
└── types/                   глобальные типы (SDK Telegram без npm-пакета)
```

Направление зависимостей соблюдается: `app → features → components / lib`.
Предметные компоненты (`MaterialRow`, `StageTrack`) лежат в своих features
именно поэтому — из `components/` нельзя импортировать `features/`.

## Отличия от стандарта бюро

1. **`next/image` не используется, вместо него обычный `<img>`.** Карточки
   собираются в императивной деке через `innerHTML` — React-компонент туда не
   вставить. Плюс при `output: 'export'` оптимизатор картинок всё равно
   отключён (`images.unoptimized`), так что `next/image` дал бы только разметку
   без выгоды.
2. **`loading.tsx` нет.** Страница статическая, серверных данных нет — Suspense
   никогда бы не показался. Загрузка карточек происходит на клиенте, и её
   состояние обрабатывает сама дека (текст об ошибке внутри колоды, чтобы не
   терять экран целиком). Пустой файл ради галочки был бы мёртвым кодом.
3. **`npm start` не применима** — см. таблицу команд выше. Название сохранено
   для единообразия.
4. **Состояние загрузки колоды живёт в самой колоде.** Карточки приходят из
   Supabase на клиенте, поэтому заглушка и текст ошибки рисуются внутри
   `.deck`, а не через `loading.tsx` (см. пункт 2).
5. **e2e не входят в CI.** Workflow гоняет lint, typecheck, unit и build.
   Playwright требует скачивания браузера на каждый прогон; для одного экрана
   это плата без отдачи. Запускать локально перед изменениями колоды.
